## 3. Contract Lock

### 3.1 Governing question

> What must remain continuous, and what may change, when a source object is reconstructed or projected across contexts, granularities, or relative levels?

### 3.2 Required claims

Chapter 5 must establish:

1. origin type identifies the analytical type of the source object within its source reconstruction and may not be retrospectively overwritten by a later target function;
2. a target function is a bounded relational role performed by a source object within a declared target context;
3. a target function is neither a new primitive, global property, permanent identity, nor automatic target-object type;
4. transformation context declares the relation-space within which an operation possesses analytical purchase and validity, including purpose, target context, relevant sources, temporal reach, and claim ceiling;
5. frame and transformation context may overlap but remain non-equivalent;
6. reference continuity, type integrity, functional continuity, and temporal continuity are separately testable and may produce different local results;
7. contextual boundedness prevents local functions from being inherited by parallel, later, wider, or unrelated contexts without a new test;
8. a useful analogy may remain `analogy_only` where functional continuity is not established;
9. continuity failure may require reduction, provisionality, failure, Stop, or Non-Capture rather than one automatic all-or-nothing result;
10. the Minimal Projection Form is conceptual prose mapped to existing Shared Transformation Record paths, not a second schema.

### 3.3 Required distinctions

| Distinction | Required Chapter 5 burden |
| --- | --- |
| origin type vs. operator type | origin type is the source object’s declared analytical typing and need not be one of the abstract Δ–Ψ types |
| origin type vs. target function | preserve source typing while declaring a separate bounded function |
| source frame vs. target frame | declare the reconstruction coordinate on each side without treating frame change as function proof |
| frame vs. target context | a frame bounds reconstruction; a target context is the scene or relation in which a function is proposed |
| target context vs. transformation context | target context is the target-side setting; transformation context governs the operation relation, purpose, sources, validity, and claim ceiling |
| reference continuity vs. nominal sameness | require historical/reference and constitutive relation support rather than unchanged naming |

| functional continuity vs. metaphorical association | require source-carried function and material source-change sensitivity |
| temporal continuity vs. complete chronology | preserve the relevant historical order and load without requiring exhaustive detail |

| projection without replacement vs. full retyping | `PROJECT_AS` adds a bounded relation; it does not replace the origin type |

Chapter 5 must not claim that:

- a target function changes or supersedes the origin type;
- origin type is always a PMS operator type;
- functional resemblance proves operator identity or functional continuity;
- unchanged naming proves reference continuity;
- a valid function can be asserted without target context, validity scope, and source trace;
- functional continuity is source-independent;
- context fit alone proves a target function;

## 5. Core Concept Architecture

### 5.1 Origin Type

**Preparation definition**

The origin type is the declared analytical type under which the source object is identified in its source reconstruction before a later target function is assigned or tested.

It may be, for example:

- operator-typed occurrence;
- composite structure;
- configuration;
- event or non-event structure;
- transition;
- sequence;
- path;
- trajectory;
- another already warranted derived analytical object.

It is not automatically one of the abstract Δ–Ψ operator types.

```text
origin type
≠ operator type automatically
≠ target function
≠ permanent essence
```

The origin type may be provisional. Preserving it does not make the underlying source claim infallible. A valid later function may coexist with a provisional origin claim, provided the provisionality and the exact source load supporting the function remain explicit.

For `PROJECT_AS`, origin-type preservation is mandatory. `COMPOSE` may form a new target object and `DECOMPOSE` may reconstruct an object more finely, but neither operation may retrospectively rewrite what the source object had been typed as in a prior record. A new target object receives its own typing; a finer reconstruction may revise the warranted source claim; neither action edits history by renaming the earlier source type.

### 5.2 Target Function

**Preparation definition**

A target function is a bounded relational role that an origin-typed source object performs within a declared target context for a specified analytical purpose and validity scope.

```text
target function
= context-bound relation
not object-type replacement
```

A target function must be:

- precisely named;
- carried by identifiable source features;
- relevant to the target context;
- bounded in time, scene, relation, and claim reach;
- sensitive to material changes in its load-bearing source features;
- defeasible and revisable;
- distinct from analogy, label substitution, and authority.

The same source object may support different compatible functions in different target contexts. This does not create multiple origin types. Each function is a separate claim with its own target context, source trace, validity scope, and failure conditions.

```text
same source object
+ different target contexts
→ potentially different compatible functions
```

This is not unlimited functional elasticity. If almost any source could perform the same function regardless of its specific structure, the function has lost constitutive source trace.

### 5.3 Target Context and Transformation Context

The chapter must use both terms without collapse.

A **target context** is the target-side scene, relation, configuration, or analytical use within which a target function is proposed.

A **transformation context** is the declared relational envelope within which the operation possesses analytical purchase. It includes at least:

- the operation occurrence and purpose;
- source and target reference relation;
- relevant source and target coordinates;
- target context;
- sources considered relevant;
- temporal reach and duration of the function claim;
- validity scope;
- Claim Ceiling and exclusions;
- uncertainty and revision conditions.

```text
frame
→ bounds a reconstruction

target context
→ identifies the target-side scene or relation

transformation context
→ governs the source–operation–target relation,
  purpose, source relevance, validity, and claim ceiling
```

The three may overlap in a simple case, but they do not become synonyms.

### 5.4 Reference Identity and Reference Continuity

**Reference identity** asks what historical or analytical object the claim is about. **Reference continuity** asks whether that object remains sufficiently identifiable through the tested transformation relation.

Minimum questions:

- Is the source object still identifiable?
- Does the later claim concern the same historical process or explicitly a derived target object?
- Are constitutive relations preserved or openly revised?
- Has a new object been substituted while the old name remains?
- Are source and target reference boundaries declared?
- Does the transformation preserve the conditions that made the source object identifiable?

```text
same name
≠ same reference object
```

Reference continuity differs by operation:

- `COMPOSE` creates a new composite while preserving traceable source references;
- `DECOMPOSE` must retain the same reference object as reconstruction target;
- `PROJECT_AS` must retain the source reference while adding a bounded target function.

A nominally identical object may fail continuity if the source basis, constitutive relation, temporal boundary, or actual referent changes.

### 5.5 Type Integrity and Type Continuity

Type integrity requires that source typing, target-object typing, and target function remain explicit and non-substitutable.

For `PROJECT_AS`:

```text
origin type preserved: required

target function declared separately: required

origin type replaced by function: prohibited
```

Reference continuity may pass while type integrity fails. An analyst may still point to the same historical trajectory but falsely declare that it has become `Frame` as an origin type. The referent remains identifiable; the typing claim fails.

Type continuity is not rigid immunity from revision. New evidence or a warranted finer reconstruction may require a new, explicitly revised typing claim. The prohibition concerns **unmarked or retrospective replacement**, especially replacement caused only by a useful later function.

### 5.6 Functional Continuity

Functional continuity requires a traceable relation between load-bearing source features and the proposed target function.

Minimum criteria:

1. the target function is precisely specified;
2. constitutive source features are identified;
3. those source features matter to how the function operates;
4. a relevant source change would weaken, alter, or defeat the function;
5. the function remains bounded to a declared target context and validity scope;
6. rival functions, analogy, and no-projection alternatives remain visible;
7. the function does not inherit authority from usefulness or structural fit.

```text
source-independent function
→ functional discontinuity or empty label
```

Functional continuity may be:

- supported;
- supported only under a narrowed claim;
- provisional;
- partially supported across separable features;
- below function threshold but retained as `analogy_only`;
- failed;
- unresolved under Non-Capture.

Chapter 5 must not force one binary outcome for every continuity dimension.

### 5.7 Temporal Continuity

Temporal continuity requires that the historically relevant order, duration, heterogeneity, and carried load remain reconstructible at the level needed by the target claim.

It does **not** require an exhaustive chronology or preservation of every detail.

```text
temporal continuity
≠ complete chronology
≠ losslessness
```

The chapter must prevent:

- later function from deleting the earlier path or trajectory;
- macro-compression from turning a duration into one point without disclosure;
- a trajectory from becoming a timeless property;
- a later context from rewriting earlier uncertainty as settled history;
- later relevance from proving earlier inevitability or teleology.

A projection may be temporally continuous while still compressing detail, provided the relevant ordering and historical load remain traceable and loss is explicit.

### 5.8 Contextual Boundedness

Contextual boundedness limits the target function to its declared target context, temporal reach, relative level, analytical purpose, and validity scope.

It requires:

- no automatic transfer to parallel contexts;
- no automatic persistence into later configurations;
- no function inheritance across levels or domains;
- no universalization from one scene;
- no authority inheritance;
- explicit revision and re-entry conditions.

```text
valid here
≠ valid elsewhere
≠ valid indefinitely
≠ authorized action
```

A new context requires a new testable function claim. Prior success is relevant source material but not inherited validity.

## 6. Continuity Matrix and Interaction Rules

### 6.1 Separate dimensions

The chapter must use a four-part continuity declaration:

| Dimension | Governing question | Can pass while another fails? |
| --- | --- | --- |
| reference continuity | Is the relevant source or historical object still identifiable? | yes |
| type integrity / type continuity | Is source typing visible and free from unmarked replacement? | yes |
| functional continuity | Is the target function carried by specific source features? | yes |
| temporal continuity | Is relevant historical order and load preserved at the required claim level? | yes |

Contextual boundedness is a cross-cutting validity condition rather than a fifth interchangeable continuity type.

### 6.2 Non-compensation

```text
strong reference continuity
cannot compensate for failed type integrity
```

```text
strong type integrity
cannot compensate for absent functional continuity
```

```text
functional usefulness
cannot compensate for temporal discontinuity
```

```text
contextual fit
cannot compensate for missing source trace
```

Formal elegance, completeness, or source volume cannot compensate for a failed load-bearing continuity dimension.

### 6.3 Partial failure and claim effect

The chapter must preserve the possibility of different bounded outcomes:

| Finding | Possible local effect |
| --- | --- |
| all required dimensions carried within scope | `admissible` or `admissible_with_bounded_claim` candidate |
| support depends on unresolved source or timing issue | `admissible_but_provisional` candidate |
| separable functional segments differ | `partially_admissible` candidate |
| analogy remains but source-carried function fails | `analogy_only` |
| broader function exceeds continuity burden | `claim_reduction_required` |
| declared projection lacks constitutive conditions | `failed_transformation` |
| type replacement or unbounded continuation is insisted upon | `mandatory_stop` |
| rival functions or referents cannot be responsibly resolved | `non_capture` |

These are candidate mappings for later local tests. Chapter 5 does not replace Chapter 6 or Chapter 47 routing procedures.

## 7. Running Example and Counterpressure Architecture

### 7.1 Shared source family

Chapter 5 continues the bounded project-review source family used in Chapters 1–4:

```text
K0
→ E1 / T1
→ K1
→ N1 / T2
→ K2
→ P_review
```

`P_review` is a composed review path with origin type `path`. The positive projection asks whether this path may perform a bounded **frame-function** in one later configuration `K3` by orienting attention toward promised reconsideration, accumulated reopening burden, and the difference between completed adoption and non-realized review.

The function is not an origin-type replacement:

```text
origin type: path

target function in K3:
bounded frame-function for one process-review question
```

### 7.2 Required positive example

The minimal positive example must declare:

- source object: `P_review`;
- origin type: path;
- source level and source coordinates;
- target context: later process-review configuration `K3`;
- target level and target coordinates;
- target function: bounded frame-function for reviewing promised reconsideration and reopening burden;
- validity scope: the named review question in `K3`;
- load-bearing source features: ordered adoption, promise, bounded non-realization, transition effects, and accumulated procedural residue;
- source-change sensitivity;
- alternatives: analogy-only, another bounded function, or no projection;
- continuity matrix;
- loss and uncertainty.

Expected bounded candidate:

```text
admissible_with_bounded_claim
```

### 7.3 Same source, different compatible functions

The same `P_review` may support a second compatible function in another target context `K4`, for example a **memory-function** limited to reconstructing why a reopening request carries accumulated procedural residue.

```text
same source path
+ K3
→ bounded frame-function

same source path
+ K4
→ bounded memory-function
```

Each function needs its own record, source trace, target context, validity scope, and failure test. The multiplicity does not turn the path into a universal Frame or Memory type.

### 7.4 Relevant source-change pressure

A counterfactual variant removes or materially weakens `N1`, the source-supported non-realization of promised review. The frame-function centered on promised reconsideration and reopening burden must then weaken, change, or fail.

```text
material source change
→ target-function change required
```

If the same target function remains unchanged despite removal of a load-bearing source feature, functional continuity has failed.

### 7.5 Provisional origin claim with bounded function

A later function may remain locally useful while one component of the source path remains provisional. The function claim must inherit the source uncertainty as a limitation rather than convert it into certainty.

```text
provisional source component
+ explicit limitation
→ bounded provisional function may remain
```

### 7.6 Reference preserved, type integrity failed

A negative case keeps the same `P_review` referent but declares:

```text
P_review has become Frame as origin type
```

Reference continuity may remain positive, while type integrity fails. The stronger retyping claim must be rejected or stopped.

### 7.7 Analogy below functional continuity

Another countercase says that the path is “like a frame” because it highlights some later issues, but provides no precise target function, validity scope, or source-change test.

The resemblance may remain:

```text
analogy_only
```

The stronger `PROJECT_AS` claim does not survive.

### 7.8 Nominal sameness without continuity

A later document uses the same label `P_review` for a different collection of meetings, omits the original promise and non-event structure, and changes the temporal boundary. The name remains; the referent and constitutive relation do not.

```text
same label
≠ reference continuity
```
